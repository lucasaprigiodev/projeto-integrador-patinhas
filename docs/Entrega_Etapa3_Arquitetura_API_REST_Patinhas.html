1. Diagrama da Arquitetura Distribuída

O sistema Patinhas foi evoluído para uma arquitetura cliente-servidor distribuída em três camadas desacopladas. As interfaces de usuário (Aplicativo Mobile Android empacotado com Capacitor e Painel Web Administrativo da ONG) não manipulam dados isoladamente: todas as operações passam pelo módulo de comunicação HTTP (www/db.js), que envia requisições padronizadas em JSON com autenticação JWT para o servidor API HTTP/REST (backend/server.js), responsável por validar regras de negócio, controlar permissões (RBAC) e persistir os registros no banco de dados relacional SQLite (backend/patinhas.sqlite).

2. Modelagem e Persistência de Dados Relacional

2.1 Entidades, Relacionamentos e Regras de Integridade

O esquema relacional foi definido no arquivo backend/schema.sql e instanciado automaticamente por backend/database.js com suporte explícito a chaves estrangeiras (PRAGMA foreign_keys = ON;). O modelo contempla quatro entidades principais:

1:N com adocoes_matches
1:N com mensagens		 UNIQUE(email), UNIQUE(cpf), CHECK(perfil IN ('adotante','ong')), senha com hash scrypt.

2.2 Justificativa da Escolha do Banco de Dados Relacional (SQLite)

Optou-se pelo banco de dados relacional SQLite 3 integrado nativamente ao motor do Node.js (módulo node:sqlite / DatabaseSync) pelos seguintes motivos técnicos e arquiteturais:

1. Conformidade Relacional e Transações ACID: O SQLite implementa o padrão SQL relacional completo, garantindo atomicidade, consistência, isolamento e durabilidade (ACID), além de impor restrições de chave estrangeira (FOREIGN KEY), unicidade (UNIQUE) e validação de domínio (CHECK) diretamente no nível do banco.
2. Persistência Real em Disco e Portabilidade Acadêmica: Todos os dados são gravados de forma durável no arquivo binário backend/patinhas.sqlite operando em modo Write-Ahead Logging (PRAGMA journal_mode = WAL;). Ao reiniciar o servidor Node.js, todas as contas criadas, animais cadastrados, matches, assinaturas de termos e mensagens de chat permanecem intactos, sem depender de containers externos complexos para avaliação da banca.
3. Carga Inicial Automatizada (Seeds): Ao iniciar pela primeira vez, backend/database.js popula automaticamente 3 usuários (incluindo a conta administrativa admin@ong.com e o adotante lucas@ifrn.edu.br), 6 animais disponíveis e um processo de adoção com histórico de mensagens para testes imediatos.

3.2 Justificativa da Arquitetura REST em Comparação ao SOAP

Para a construção da camada de comunicação distribuída do projeto Patinhas, escolheu-se o estilo arquitetural REST (Representational State Transfer) sobre HTTP com payloads em formato JSON, em detrimento do protocolo SOAP (Simple Object Access Protocol). A decisão fundamenta-se nos seguintes critérios técnicos:

Critério Técnico Arquitetura REST (Escolhida no Projeto) Protocolo SOAP
Formato de Dados e Overhead de Rede Utiliza JSON, formato leve e compacto, reduzindo drasticamente o consumo de banda e bateria em dispositivos móveis (Android/Web). Exige envelopes XML verbosos (<soap:Envelope>, <soap:Header>, <soap:Body>), aumentando o tamanho das mensagens e a latência.
Semântica do Protocolo HTTP Aproveita nativamente os verbos HTTP (GET, POST, PUT, PATCH, DELETE) e códigos de status padronizados (200, 201, 400, 401, 403, 404, 409, 422). Opera geralmente encapsulado apenas em requisições POST, ignorando a semântica de cache e status nativos do HTTP (erros vêm em SOAP Fault).
Acoplamento e Consumo no Frontend Nativo no JavaScript moderno via fetch() e JSON.parse() no módulo db.js, sem necessidade de bibliotecas pesadas de parsing no celular. Exige contratos rígidos em WSDL e bibliotecas especializadas de serialização/parsing XML, dificultando a evolução ágil das telas.
Escalabilidade e Estado (Stateless) Totalmente stateless: cada requisição carrega seu próprio token JWT Bearer, facilitando escalabilidade horizontal e cache. Frequentemente acoplado a extensões complexas como WS-Security e estado de sessão pesado no servidor.

4. Identificação, Autenticação JWT e Controle de Acesso (RBAC)

O servidor substituiu qualquer login simulado por autenticação real persistida na tabela usuarios. As senhas são armazenadas exclusivamente sob derivação criptográfica (crypto.scryptSync com salt) e verificadas com comparação em tempo constante (crypto.timingSafeEqual). Ao autenticar em POST /api/auth/login, o servidor emite um token JWT (HMAC-SHA256) contendo id, email e perfil (adotante ou ong).

  • Tentativas sem autenticação (401 Unauthorized): O middleware authenticateToken intercepta rotas protegidas e recusa imediatamente requisições sem cabeçalho Authorization: Bearer <token> ou com assinatura JWT inválida/expirada.
  • Tentativas com permissão insuficiente (403 Forbidden): O middleware requireRole('ong') valida no servidor o perfil do usuário autenticado. Um usuário adotante não consegue cadastrar/excluir animais (POST/DELETE /api/pets), enviar termos (POST /api/matches/:id/enviar-termo) nem aprovar adoções (PATCH /api/matches/:id/status). Além disso, na rota GET /api/matches, um adotante consulta exclusivamente os seus próprios processos (filtrados por adotante_id = req.user.id).

5. Resumo das Rotas Documentadas no OpenAPI 3.0 (Swagger)

A especificação completa encontra-se em backend/openapi.json e na interface interativa swagger.html (ou em http://localhost:3000/api-docs quando o servidor está em execução):

Método Caminho (Endpoint) Permissão / Auth Descrição e Códigos HTTP Retornados
POST /api/auth/register Público Cadastra novo usuário (adotante ou ONG) e retorna JWT (201, 400, 409).
POST /api/auth/login Público Autentica e-mail/senha no SQLite e emite token JWT (200, 400, 401).
GET /api/auth/me JWT (Qualquer) Retorna dados do usuário logado a partir do token (200, 401).
GET /api/pets e /api/pets/:id Público Lista catálogo de animais ou detalhes por ID (200, 404).
POST /api/pets JWT (Perfil: ong) Cadastra novo animal vinculado ao ong_id autenticado (201, 400, 401, 403).
PUT / DEL /api/pets/:id JWT (Perfil: ong) Atualiza ou remove um animal do banco de dados (200, 401, 403, 404).
GET /api/matches JWT (Adotante/ONG) Lista matches do adotante logado ou todos os matches da ONG (200, 401).
POST /api/matches JWT (Adotante) Cria match no estado pendente e inicia chat com a ONG (201, 404, 409, 422).
POST /api/matches/:id/enviar-termo JWT (Perfil: ong) Transição pendente → termo_enviado (200, 401, 403, 404, 422).
POST /api/matches/:id/assinar-termo JWT (Dono do Match) Transição termo_enviado → termo_assinado (200, 400, 403, 404, 422).
PATCH /api/matches/:id/status JWT (Perfil: ong) Transição final para aprovado ou rejeitado (200, 400, 403, 404, 422).
GET / POST /api/matches/:id/messages JWT (Participantes) Consulta ou envia mensagens no chat vinculadas ao usuário (200, 201, 403, 404).
